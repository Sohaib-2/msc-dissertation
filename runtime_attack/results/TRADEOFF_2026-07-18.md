# Stealth-vs-Strength Trade-off — runtime hijack vs teacher-side detector

**Date:** 2026-07-18 | **Scale:** CPU prototype (see *Caveats*) | **Status:** result stands, numbers provisional

This is the central defensive result of Phase 2. It combines the two halves measured separately:

* `detector_eval_soft_pr0.1_w200.md` — how **detectable** the hijack is at each strength `alpha`
* `asr_sweep_soft_pr0.1_ep10_n4000.md` — how **effective** it is at each strength `alpha`

Both halves use the SAME clean teacher, trigger, target class (0) and poison_rate (0.1), so the two
columns describe one attack rather than two loosely-related experiments.

---

## The result

| alpha | Detection AUC | Detection TPR@5%FPR | Student ASR | Student ACC |
|---|---|---|---|---|
| 0.0 (control) | 0.500 | 0.043 | 0.060 | 0.506 |
| 0.1 | 0.553 | 0.070 | 0.061 | 0.491 |
| 0.25 | 0.679 | 0.200 | 0.079 | 0.497 |
| 0.5 | 0.997 | **0.987** | 0.282 | 0.488 |
| 0.75 | 0.997 | 0.990 | 0.676 | 0.490 |
| 1.0 | 0.999 | 1.000 | 0.827 | 0.497 |

Reference points: clean teacher ACC 0.693, ASR 0.032. Chance-level ASR is ~0.06 (the alpha=0 control).

## What it says

**1. Detection saturates before the attack becomes potent.**
Between alpha=0.25 and alpha=0.5 the detector goes from catching 20% of attacks to catching 98.7%,
while ASR only climbs from 0.079 to 0.282. The detection curve rises far faster than the attack curve.
By the time the hijack installs even a weak backdoor, it is already being caught almost every time.

**2. There is no operating point that is both effective and stealthy.**
The attacker's options are:
* `alpha <= 0.25` — evades detection 80%+ of the time, but ASR (0.079) is indistinguishable from the
  0.060 control. No backdoor is installed. The attack achieves nothing.
* `alpha >= 0.5` — a real backdoor installs, but detection is >= 98.7%.

Forcing the attacker below the detector's threshold costs them ~90% of their attack power
(ASR 0.827 -> 0.079). That is the headline number.

**3. The victim has no other signal — which is why the teacher-side detector is needed.**
Student clean accuracy is FLAT at ~0.49 across every alpha, including alpha=1.0 where ASR is 0.827.
The attack is completely invisible in the student's clean performance, so a victim monitoring
downstream accuracy would never notice. The manipulation is only visible where we chose to look:
the teacher's output stream.

**4. Per-query detection fails — and inverts.**
Per-query AUC sits at 0.35-0.40 for moderate alpha, i.e. BELOW chance. Blending a confident clean
prediction with a one-hot on a different class produces a two-peaked, HIGHER-entropy output, so
moderate hijacking makes the teacher look *less* confident, not more. Naive "suspiciously confident
output" heuristics do not merely miss this attack, they point the wrong way. This is the evidence that
stream-level monitoring is necessary rather than merely convenient.

## Why this is not circular

The obvious objection to any self-built attack + self-built detector is that the detector was tuned to
beat the attack. Three design choices pre-empt it:

* The detector is **target-agnostic** — never told class 0 is the target; its strongest signal
  (`max_class_excess`) asks only "is *any* class over-represented?"
* The detector is **trigger-agnostic** — never told what the trigger is or which queries carry it.
* The **alpha=0 control** (trigger stamped, hijack off) sits at AUC 0.500 / TPR 0.043 against a 0.05
  budget, and its student ASR (0.060) matches chance. So we are detecting the *attack*, not the trigger,
  and the backdoor comes from the hijack rather than from anything else in the pipeline.

We did not tune the detector against one attacker; we swept the attacker's own strength knob across its
full range and found the evasion window empty.

## The DEFENDER also has a knob: window size

Everything above sweeps the *attacker's* parameter (alpha) at a fixed 200-query window. But window size
is the *defender's* parameter, and it was never swept. Since the hijack must keep pushing probability
mass toward one class, the evidence accumulates — so a longer window should catch weaker attacks.

Detection TPR@5%FPR, `soft` rule, poison_rate 0.1:

| alpha | w=100 | w=200 | w=500 | w=1000 | w=2000 |
|---|---|---|---|---|---|
| 0.0 (control) | 0.003 | 0.043 | 0.050 | 0.050 | 0.050 |
| 0.1 | 0.060 | 0.070 | 0.113 | 0.227 | 0.313 |
| **0.25** | 0.073 | 0.200 | 0.330 | 0.723 | **0.997** |
| 0.5 | 0.573 | 0.987 | 1.000 | 1.000 | 1.000 |

**At alpha=0.25 — the stealthy region — the attacker's escape rate falls from 93% to 0.3% purely by
watching longer.** The alpha=0 control stays pinned at 0.050 across every window size, confirming this
is genuine evidence accumulation rather than a drift toward false alarms.

**Why this matters for the GPU run.** The main risk to the headline is that ASR rises at low alpha at
full scale, handing the attacker a working backdoor inside the stealthy region. This result is the
answer: the attacker's low-alpha advantage is not fixed. Lowering alpha to evade can be met by raising
the window to accumulate more evidence. The honest framing is therefore a trade-off between **attacker
strength and defender patience**, not a fixed threshold.

**The cost, stated plainly:** longer windows mean slower detection. A 500-query window cannot flag
anything until 500 queries have passed. This is latency traded for sensitivity, not a free win, and it
is an operational limit worth naming.

**Confirm at the large end.** w=1000 and w=2000 windows are drawn from only 5,000 held-out images, so
they overlap heavily and are far from independent. Overlap does not bias the AUC (both classes are
sampled identically) but it does shrink the effective sample size, so those two columns need
re-measuring with disjoint windows over the full test set. The monotone trend from w=100 to w=500,
where overlap is mild, is already solid.

## Caveats (state these before anyone else does)

1. **Prototype scale.** 4,000 train images, 10 epochs, ResNet-18 teacher (69.3% ACC), MobileNetV2
   student, CPU. Student ACC ~0.49 is a function of that scale, not of the attack.
2. **ASR is probably UNDER-estimated.** Students trained longer on more data typically absorb backdoors
   more thoroughly, so the real crossover may sit further left, narrowing the margin. This is the single
   most important thing the GPU run must check.
3. **Overlapping detection windows.** 300 windows sampled from 5,000 held-out images, so windows are not
   fully independent and confidence is mildly optimistic. Fix is free: disjoint windows over the full
   test set.
4. **One trigger, one target class, one architecture pair.** Generality across triggers/targets is
   untested.

None of these threaten the *shape* of the curve — the alpha=0 control is clean and the effect sizes are
far outside noise — but the exact numbers should not be quoted as final until the GPU run.
